# Algorithms & Data Structures

## Description

As with Milestone two, I have chosen to work with the CS 360: Mobile Architecture & Programming final project as my artifact.  Titled Event Tracking App, this is a program built in Android Studio, using the Java programming language, that allows users to schedule and track events through an easy-to-use UI.  In addition to CRUD capability, Event Tracking App provides the ability to schedule SMS notifications.  In its original state, this application relied on list and database functionality for basic sorting, however there was no algorithm in place for both managing events and preventing overlap.

## Justification

This artifact provided a great platform for category two improvements as most of its original event ordering came from an SQL ORDER BY query.  To meet artifact improvement criteria, I have implemented a data structure and algorithm combination that supports event data organization and demonstrates the ability to program with Big O notation in mind.  Whereas before there was no algorithm in place, I added an entire Event Scheduler class that leverages both data structures to ensure one event does not overlap with another.  This class works with a TreeSet for event ordering, and a HashMap for looking up events by ID.  The algorithm itself required the addition of both start and end event times as a means of preventing scheduling conflicts prior to storage.  In addition to ensuring event entries are consistent across both structures and Room itself, the provision of these new tools greatly improves data accessibility and application performance.  For example, using HashMap for finding events by ID receives an O (1) for Big O notation, while creating an event and placing it into the TreeSet organizational structure receives an O (log n).  As with category one, this category allowed me to focus on performance and memory improvements rather than just making something operational.

## Reflection

Course outcome three requires problem solving using algorithmic principles.  While the initial artifact had basic CRUD capability, it now uses algorithmic principles to ensure data lookup and deconfliction is done so in a way that preserves memory while maintaining efficiency.  Not only is event data either represented or persistently maintained in three application areas, but also it is done so in away that ensures information is homogenous for later CRUD operations.  I believe these enhancements meet course outcome three both in application of algorithmic principles, and their overall selection in terms of design choice.  While Big O notation is improved, one class/algorithm managing two data structures greatly increases application complexity.  Additionally, a TreeSet would have been sufficient on its own for Event Tracking App, however in balancing trade-offs, I opted for more efficient memory usage at the cost of simplicity.  These techniques also heavily demonstrate course outcome four, as each data structure employed is based on industry standard techniques and practices.  The addition of a TreeSet, HashMap, and overlap algorithm solve the problems of application memory and data deconfliction, all while working within the parameters of the MVVM architecture implemented during the category one enhancements.

This milestone taught me a lot about balancing performance with complexity when thinking about how to store and organize event data.  Different structures excel in different areas, and there is no ‘one size fits all’ combination.  While TreeSet supports ordering via a comparator, which in this case was based around previous and next events, a HashMap provides a constant O (1) for event lookup.  Attempting to combine these with an overlap algorithm taught me a lot about correct ordering of operations to support application efficiency.  For example, lower() and higher() work as a means of checking for overlap because at that point events have already been sorted.  Adding more than one data structure also becomes a balancing act when conducting CRUD operations as event information must be consistent across the entire application.  Adding an event, for example, requires Edit Event ViewModel to pull the existing event schedule and look for overlap via Event Scheduler.  Then, it communicates with event repository to insert the event.  Once Room stores it and returns an ID, Event Scheduler receives and adds it to each data structure.  Before category one and two enhancements, Add Event Activity maintained much of the logic for adding an event, while an SQL ORDER BY query handled ordering. 

The implementation of these enhancements also reinforced the importance of iterative testing, along with testing every possible CRUD scenario.  For example, comparator development required a lot of trial and error before it was able to both sort and discern duplicates.  Since two events can have the same start time, event ID had to be added as to keep them separate until eventually reaching the overlap algorithm.  Another change I had to make was in the edit event ViewModel, where the IDs of new/pending events were set as -1 prior to being saved.  The purpose of this was to act as a placeholder before being saved and receiving an actual ID, however this caused new events to retain the -1 label.  When clicking on an event card nothing would populate because events with -1 were being interpreted as new.  Thanks to a simple conditional statement, existing events maintain their ID during update, and new events can be assigned an actual database ID.
